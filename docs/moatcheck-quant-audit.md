# Historical MoatCheck codebase audit

> **Historical snapshot, not current product documentation.** This repository audit was written before the pure quant core, Supabase Auth, owner-scoped portfolio persistence, Advisor, current frontend workspaces, and daily ingestion pipeline were completed. Its implementation descriptions and gaps below reflect its original review date and should not be used to describe the current release. Use the [README](../README.md), [data-source/horizon guide](data-sources-and-advisory-horizon.md), and [current platform audit](platform-audit-2026-10-17.md) for present behavior and verification status.

Repository review for planning a transition to **MoatCheck Quant**. The detailed findings below describe the implementation at the time that review was written and are retained as historical engineering context.

## 1. High-level architecture and tech stack

- **Frontend:** Next.js 15 App Router, React 19, TypeScript 5. `output: "export"` creates static pages; interactive pages are client components using React hooks. Tailwind CSS 3 supplies utility styling and the visual system; there is no separate component library or global state framework. UI components are in `frontend/components/`; browser portfolio state is localStorage.
- **Visualization/UI packages:** Recharts for charts, Framer Motion for transitions, Lucide React for icons. Shared fetch/types live in `frontend/lib/api.ts`; pages include dashboard, stock detail, screener, portfolio, backtest, compare, methodology, qualitative feed, and admin.
- **Backend:** Python 3.12 in CI; FastAPI routes in `backend/app/api/routes.py`, with Pydantic request validation. `backend/app/main.py` mounts the API at `/api`, health at `/health`, and the exported frontend from `backend/static/` when present. There is no user/account service or general async job queue.
- **Persistence:** Supabase Postgres accessed through the Python Supabase/PostgREST client. Tables include `stocks`, `price_history`, `fundamentals`, `scores`, `refresh_queue`, `qualitative_notes`, and `feed_status` (the last two qualitative tables are extended by the qualitative migration). The browser calls FastAPI; FastAPI reads the database with the configured key. SQL enables RLS and grants public read policies; public write routes require `X-Admin-Key` and fail closed when `ADMIN_API_KEY` is absent.
- **Market data:** Alpha Vantage is the primary provider. Equities use OVERVIEW, quarterly income statement, balance sheet, cash flow, earnings, splits, and weekly price series; benchmarks and ETFs use reduced price-only paths. Finnhub is optional and used for selected fundamentals in a hybrid/fallback path with fiscal-date and magnitude checks. Historical closes are split-adjusted locally; dividends are not adjusted. Qualitative inputs are SEC EDGAR and general press RSS by default; IR RSS and Gmail newsletter collectors are implemented but disabled. Groq classifies collected events. Yahoo Finance (`yfinance`) remains a dependency and is used in the qualitative EDGAR mapping path; price-history calculations use stored Supabase data.
- **Deployment/config:** `render.yaml` builds the frontend export, copies it into the backend, installs Python requirements, and runs one Render web service. `frontend/.env.example` documents `NEXT_PUBLIC_API_URL`; backend `.env.example` documents provider/database/admin settings. A GitHub Actions workflow runs weekday refresh, score recomputation, qualitative refresh, and JSON export to Supabase Storage; it can also be dispatched manually. The JSON export is consumed by the companion mobile app. Secrets are configured as GitHub/Render environment variables. The repo also contains migrations, operational scripts, and local `.env` files; secrets were not inspected for this audit.

## 2. Existing feature inventory

- **Fundamental snapshots:** `backend/app/data/fetch.py` joins quarterly income, balance-sheet, cash-flow, and earnings data by fiscal period and persists one snapshot per ticker/quarter. Metrics include revenue, YoY revenue growth, operating/net margin, TTM ROE, net debt/TTM EBITDA, TTM free cash flow, trailing P/E, market cap, and nullable ROIC/forward P/E. `know_date` is fiscal period end plus a 60-day assumed reporting lag. Missing provider fields remain null.
- **Fundamental score:** `backend/app/scoring/fundamentals.py` linearly normalizes revenue growth (0–30%), operating margin (0–35%), ROE or ROIC (0–30%), net debt/EBITDA (best at net cash, zero at 4x), and positive FCF. Default component weights are 25/20/25/15/15%. Missing fields are omitted and weights renormalized; debt/EBITDA is excluded for financial services. Although the field and scorer support ROIC precedence, ingestion documents ROIC as unavailable/null, so practical scoring uses ROE.
- **Risk and composite scores:** `backend/app/scoring/risk.py` computes weekly returns, annualized volatility and Sharpe/Sortino (52 periods/year; 3% risk-free rate), max drawdown, and correlation/covariance. Risk score averages normalized volatility, Sharpe, and drawdown equally; Sortino is informational only. At least 26 price points are needed for most risk statistics. Composite score is 60% fundamentals / 40% risk, renormalizing when one side is absent.
- **Qualitative events:** Despite older README wording, the code implements a separate event pipeline (`backend/app/qualitative/`). EDGAR and press sources are enabled; IR RSS and Gmail are disabled. Groq classification emits categories, sentiment, severity, confidence, event date, summary, and source metadata; deduplication and feed health are tracked. API/UI show timelines and rolling 90-day sentiment counts. Comments and route behavior explicitly keep this signal out of fundamental, risk, and composite scoring.
- **Portfolio page:** This is a browser-local collection of tickers, not a persisted user portfolio or account-backed holding ledger. `frontend/app/portfolio/page.tsx` stores ticker selection and displayed/manual weight state under `moatcheck_portfolio` in localStorage. It displays stock scores, weekly return correlation, inverse-volatility weights, and an efficient-frontier chart. Calculations are requested from the backend and rerun on ticker-set changes; the user-entered/local weight state is not a portfolio analytics input to those optimization APIs.
- **Portfolio calculations:** `backend/app/scoring/portfolio.py` calculates annualized volatility and inverse-volatility weights, and uses NumPy/SciPy SLSQP for long-only Markowitz optimization. Covariance is annualized and based on date-aligned weekly return observations. The frontier samples 15 target returns; it also returns a global minimum-variance point and a max-Sharpe point. Weights are bounded [0,1], sum to one, use 3% risk-free rate, and expected returns are historical weekly mean × 52. The endpoint reports excluded assets and convergence failures.
- **Backtest:** `backend/app/backtest/engine.py` offers default top-N selection (default 5), exact manual ticker baskets, and optional monthly/quarterly rebalance with configurable transaction-cost bps (default 10). At each selection date it scores using prior prices and the newest fundamental snapshot whose `know_date` has passed; no known fundamental snapshot means exclusion. Initial static baskets are equal-weighted. Rebalanced baskets are reselected and chained with turnover costs. Results include basket/benchmark curves, metrics, selections, scores, exclusions, and rebalance details.
- **Other analysis:** screener filters by sector, score, growth, risk score, market cap, P/E, and debt/EBITDA; compare plots normalized stored price curves; correlation returns a weekly return matrix. Admin operations add/curate tickers and feeds, trigger refresh and recompute, or run qualitative ingestion.
- **Key data shapes:** `stocks` stores ticker identity, sector/industry/currency, equity/ETF type, benchmark flag, status, and optional sector benchmark/feed URL. `price_history` stores `(ticker, date, close, volume)` with a ticker-date uniqueness constraint. `fundamentals` stores ticker/report/know dates, nullable numeric ratios, source metadata, unique ticker/report date. `scores` stores timestamped component metrics/scores and JSON breakdown. Portfolio selection/weights are a browser JSON object; optimization outputs are transient API responses and are not persisted as portfolios.

## 3. Portfolio optimization deep-dive

- **Location:** Core algorithms are backend Python in `backend/app/scoring/portfolio.py`; shared return/covariance functions are in `backend/app/scoring/risk.py`; stored closes are loaded by `backend/app/backtest/engine.py::_load_closes`. Routes are `GET /api/portfolio/weights`, `GET /api/portfolio/efficient-frontier`, and `GET /api/correlation` in `backend/app/api/routes.py`. Frontend orchestration/charting is in `frontend/app/portfolio/page.tsx` and `frontend/components/EfficientFrontierChart.tsx`.
- **Inputs:** Comma-separated ticker list. Routes require at least two known tickers and at least 26 stored weekly close points each. No starting weights, target risk, sector limits, max position, shorting, turnover, or user-defined constraints are accepted. These are historical-data estimators, not forward-looking capital-market assumptions.
- **Inverse-volatility output:** `weights` mapping and `excluded` reasons; weight is proportional to 1/annualized volatility, normalized to 1.0 across usable tickers.
- **Efficient-frontier output:** included tickers, exclusions, up to 15 minimum-variance points (`target_return`, `volatility`, `weights`), skipped targets, min-variance point, max-Sharpe point (`expected_return`, `volatility`, `sharpe_ratio`, weights), and explanatory note. A failure to converge or fewer than two usable assets becomes an explicit 422 API error.
- **Correlation output:** ticker ordering and a square matrix of rounded pairwise weekly-return correlations, using common dates. It is not a saved portfolio-level risk report.

## 4. Code quality, coupling, and extensibility

- **Good extraction seams:** Fundamental construction/scoring (`data/fetch.py`, `scoring/fundamentals.py`), risk functions (`scoring/risk.py`), composite scoring, and most portfolio optimizers are already in separate Python modules and can form a Core Quant Engine boundary. Their inputs/outputs are mostly plain dicts, pandas series/dataframes, and numeric values. The portfolio module currently imports a DB-bound close loader, so a reusable engine should accept price/return arrays or a provider interface instead.
- **Coupling:** API routes coordinate validation, direct Supabase queries, calculations, and response formatting in one large module. Backtest scoring queries fundamentals and sector data inside per-ticker selection loops. Frontend pages own fetch lifecycles and UI state; there is no shared query/cache/state layer. Styling is utility-class based rather than tokens/components from a formal design system. The API client has hand-written TypeScript shapes that can drift from Pydantic response structures.
- **Fetch/query scaling:** `screener()` performs latest-score and latest-fundamentals lookups per active ticker, creating N+1 PostgREST calls. Backtest `_score_at()` reads fundamental rows and sector separately for every ticker at each selection/rebalance date, magnifying calls with universe × rebalance count. Some detail/list helpers batch scores, but fundamentals and screener paths are inconsistent. `_load_closes()` paginates every price row; correlation/portfolio endpoints load each ticker independently and then invoke loaders again in optimization helpers, causing repeated DB work. Scores and full fundamentals/price histories have no visible retention policy.
- **Runtime/render characteristics:** API routes are synchronous and use synchronous Supabase calls, pandas/NumPy, SciPy SLSQP, provider HTTP, and `time.sleep` retries/throttles. Long refresh/classification requests therefore occupy request workers; no background worker or task queue is wired in. The portfolio page can issue three backend analytics requests whenever its selected ticker set changes. This is modest for a small universe but will scale poorly for broad universes and interactive multi-user work. Static export with client-side fetch means data is not rendered into the build and initial views depend on backend availability/cold start.
- **Model/data limitations relevant to platform evolution:** Weekly prices limit intraperiod drawdown detail and the sample length to about five years. Historical fundamentals' `know_date` is an explicit but approximate 60-day lag, not actual filing acceptance time. Returns/covariance and expected returns are historical estimates; no explicit corporate-action/dividend total-return series is used. Score thresholds/weights and risk-free rate are module constants. Portfolio optimizer currently has long-only full-investment constraints and no transaction/tax/liquidity/sector constraints; its unconstrained use of annualized historical mean returns can be unstable.
- **Multi-role platform gaps:** No user identity/authorization model, per-user workspaces, role permissions, persisted portfolio ownership, portfolio versioning, audit trail, or job status API is present. The single admin key protects a few write operations; public reads expose shared research data. These are architectural gaps rather than implemented capabilities.

- API and application wiring: `backend/app/api/routes.py`, `backend/app/main.py`

- Deployment/automation: `render.yaml`, `.github/workflows/refresh.yml`
